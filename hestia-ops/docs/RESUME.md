## 二、项目怎么讲（2 分钟版）

> 先讲业务价值，再讲技术难点，最后讲取舍。

「这是一个物业设施运维系统。传统物业报修靠微信群，工单散在聊天记录里，超时没人跟进、责任说不清。

我把它拆成四个机制：

**第一是状态机**。工单有 9 个状态，我没有到处 `setStatus`，而是把合法流转做成一张表，所有变更走同一个入口，非法跳转直接抛异常。这样返工、拒单这些边界情况不会产生脏数据，前端按钮也是从后端拿的可流转列表，不用两边各写一套。

**第二是 SLA**。建单时按优先级算出响应和解决两个截止时间，定时任务每分钟扫一次，超时就打标并升级通知主管。提前 30 分钟会预警，用 Redis 做了去重，避免同一单反复提醒。

**第三是派单**。三个因子打分：技能匹配 60 分、负载余量 30 分、距上次派单间隔 10 分。技能不匹配不直接排除，只是分数低，保证极端情况有人可派。候选人列表带评分明细，派单过程可解释。

**第四是巡检**。计划支持每日/每周几/每月几号，按周期推演生成任务，用唯一索引加生成前校验做幂等。巡检发现异常可以一键转工单，设备状态同步改成维修中，形成闭环。」

## 三、高频追问与回答要点

### Q1：为什么用状态机，不用 if-else 判断？

**要点**：
- 状态从 9 个，任意两个状态之间有 81 种组合，if-else 会变成网状判断，改一个状态要动很多地方
- 流转表把「允许的边」显式声明出来，新增状态只改一处
- 校验和前端按钮共用 `allowedNext()`，不会出现「前端能点、后端报错」
- 审计日志能追溯到「谁在什么状态做了什么」

**可以主动补一句**：如果状态和流转再复杂（比如多实体联动），会考虑引入 Spring StateMachine 或自研 DSL，但当前规模用枚举足够，引入框架反而增加理解成本。

### Q2：状态机怎么保证并发安全？

**诚实回答**：
- 当前是「查询 → 校验 → 更新」三步，在事务内完成，但没有加乐观锁
- 极端情况下两个请求同时读到「待派单」，都可能通过校验
- **改进方案**：给 `wo_order` 加 `version` 字段，update 时带 `where version = ?`，失败重试；或者用 `update ... where id = ? and status = ?` 做状态 CAS
- 这是我明确知道的改进点，不是没想到

> 这个问题面试官大概率会问，主动承认 + 给出方案，比硬撑「我用了分布式锁」更可信。

### Q3：SLA 超时为什么用轮询，不用延迟队列？

**对比**：
| 方案 | 优点 | 缺点 |
|---|---|---|
| 定时轮询（当前） | 实现简单、无额外中间件、漏扫可补偿 | 有最长一个扫描周期的延迟、DB 压力随工单量线性增长 |
| Redis ZSet 延迟队列 | 精度高、可精确到秒 | 需要处理 Redis 持久化与重投 |
| RocketMQ 延迟消息 | 精度高、天然支持重试 | 引入 MQ，运维成本高 |

**回答**：当前工单量级下轮询够用，扫描 SQL 走 `idx_resolve_deadline` 索引，每次最多取 200 条。如果量级上来，我会换成 Redis ZSet：`score` 存截止时间戳，定时任务只取 `score < now` 的成员，把全表扫描变成范围查询。

### Q4：派单算法的权重怎么定的？

**要点**：
- 技能是硬门槛，权重最高（60）
- 负载决定公平性（30），避免一个人堆 10 单、其他人闲着
- 派单间隔（10）是防抖，避免同一人连续被派
- 技能不匹配不排除，是为了「没有匹配的人时仍能派出去」，业务上比「派不出去」可接受

**可以补**：权重是经验值，真实场景应该用历史数据回归，比如用「平均解决时长」和「返修率」反过来调权重。

### Q5：工单号为什么用 Redis？Redis 挂了怎么办？

**要点**：
- 工单号要「人可读 + 全局唯一 + 有序」，`WO + 日期 + 4 位序号` 满足
- Redis `INCR` 原子自增，多实例下不会重复
- **坑**：Redis 重启后计数从 0 开始，会和历史数据撞号 → 我的处理是每次生成前用数据库当天最大序号校准，取两者较大值
- Redis 完全不可用时降级为时间戳后缀，保证建单不阻塞（可用性优先于号段规整）

> 这个「校准」细节是我实际踩坑后加的，讲出来比较加分。

### Q6：巡检任务怎么保证幂等？

**两层**：
1. 数据库唯一索引 `(plan_id, device_id, plan_date)`，重复插入直接报错
2. 生成前 `count` 校验，已存在就跳过

另外加了「生成窗口校验」：计划的下次生成日期如果还在未来（超出提前天数），直接返回 0。否则连续点「立即生成」会把未来几期任务一次性抽干。

### Q7：数据库为什么不用外键？

**要点**：
- 外键在高并发写入时会有额外的锁开销
- 分库分表后外键无法跨库
- 一致性由应用层（事务 + 校验）保证
- **但要承认代价**：可能出现孤儿数据，需要定期对账脚本

### Q8：哪里会成为瓶颈？

**分层回答**：
- **DB**：工单表数据量最大，按 `create_time` 做冷热分离，历史工单归档
- **列表查询**：`order by field(status,...)` 会导致 filesort，量大时改成按状态分表或加联合索引
- **报表**：当前是实时聚合，量大后改成定时预计算 + 结果表
- **通知**：WebSocket 单机维护 session，多实例需要引入 Redis Pub/Sub 或网关广播

### Q9：这个项目和外卖/电商项目有什么区别？

> 如果面试官问到这，说明他在判断项目的真实性。

**回答**：领域模型完全不同。

- 外卖的核心是「商品-购物车-订单-配送」，是**交易**模型，关注库存、支付、履约时效
- 运维的核心是「工单-派单-处理-验收」，是**服务过程**模型，关注状态流转、责任归属、时效考核

具体差异：
- 外卖订单状态是线性的（下单→支付→配送→完成），工单是**有回退和返工**的（拒单回派单池、验收驳回返工）
- 外卖没有「派单」概念（骑手由系统批量分配），工单需要「技能匹配 + 负载均衡」
- 外卖没有「巡检」这类**周期性主动任务**，这是运维特有的
- 外卖的 SLA 是「送达时间」，工单的 SLA 是「响应 + 解决」双段考核

## 四、可以主动展示的东西

面试时如果允许演示，按这个顺序：

1. **工作台**：一眼看到待受理、处理中、SLA 超时
2. **工单列表 → 详情**：展示状态机流转日志（时间线），说明「每次变更都有记录」
3. **派单看板**：展示候选人评分和 `reason` 字段，说明「派单不是黑盒」
4. **工单详情点「验收驳回」**：展示状态回到「处理中」、返工次数 +1，说明「有回退路径」
5. **巡检计划 → 立即生成**：展示任务生成，再说「再点一次不会重复」
6. **报表页**：SLA 达成率、工程师绩效、Excel 导出

## 五、如果被问「这是你自己做的吗」

诚实回答项目的来源和你的工作边界，比含糊其辞更安全。可以这样说：

> 「这个项目的业务是我自己设计的，代码是在一个开源脚手架基础上做的。底层的分层结构、JWT 鉴权、分页这些是现成的，我主要做了三件事：一是重新设计领域模型，把原来的商品订单模型换成工单派单模型；二是实现了状态机、SLA 扫描、派单算法、巡检生成这几个核心逻辑；三是重写了全部前端页面。
>
> 面试官如果继续问某个模块，我能讲到 SQL 和具体的取舍。」

**不要把开源脚手架说成从零手写**——面试官稍微问深一点就能看出来，得不偿失。
重点是：你能不能讲清楚每一层的设计原因。
